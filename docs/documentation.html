OVERVIEW

International Addressing Standards

Comparison of UPU S42 and ISO 20022 for global address management.

Two Standards, Two Purposes

UPU S42 — Postal Addressing

  • Scope: Global postal addressing standard
  • Focus: Logical structure of postal addresses for mail delivery
  • Application: Postal operations and cross-border mail
  • Flexibility: Adaptable by any country

ISO 20022 — Financial Messaging

  • Scope: Financial transaction data format
  • Focus: Structured data for financial transactions
  • Application: Banking, payments, regulatory compliance
  • Coverage: Only 32 countries

Key Differences

AspectUPU S42ISO 20022
TypePostal addressing standardFinancial messaging standard
StructureGeneric elements + country templatesHighly structured XML tags
AdaptabilityFlexible, country-specificRigid, fixed format
Best ForWeb applications, mail deliveryFinancial operations, compliance

Recommendation

UPU S42 is the better choice for most address management scenarios due to its

flexibility and wider country coverage. See UPU-S42 and ISO-20022.

UPU S42

UPU S42 Addressing Standard

Universal Postal Union framework for postal addressing.

The UPU S42 standard provides a comprehensive framework for postal addressing, designed to accommodate the diverse formats used by different countries. It includes a generic list of address elements and country-specific templates to guide users in formatting addresses correctly for mail delivery.

Key Features

  • Universal framework adaptable by any country
  • Generic list of address elements
  • Country-specific templates
  • Promotes efficient mail processing and data verification
  • Designed for easy adaptation by web applications
ISO 20022

ISO 20022 Address Schema

Financial messaging standard for transaction data.

ISO 20022 defines a standardised, structured data format for financial messaging, including specific, granular fields for address components, primarily for efficiency and accuracy in financial transactions.

> [!warning] Important

> ISO 20022 currently only applies to 32 countries.

Evolution

The standard has evolved, with the 2019 version (PostalAddress24) offering a more detailed 15-field structure compared to the 2009 version (PostalAddress6).

Components and responsibilities

ComponentResponsibility
poc-address-app.htmlStatic app markup, styles, UI behavior, sample search results, and sample verification responses.
loqate-client.jsCalls the local FastAPI search and retrieve endpoints and maps responses for the browser UI.

Map preview and zoom

The search results map is a compact 165-pixel preview, like the Asset POC. Click the preview or its expand button to open a full-size interactive map. Result markers remain selectable in both views; the expanded map supports panning and zooming.

Framework and runtime

The app uses the same no-framework approach as the Asset POC: static HTML, CSS, and browser-native JavaScript. The Loqate API key field is in the address search section. The FastAPI proxy exposes /health, /heartbeat, /api/addresses/search, and /api/addresses/retrieve; interactive OpenAPI documentation is available at /docs. The proxy can run in a local Podman container.

Without an API key, the app only returns its two built-in sample address searches. With a key, the browser sends the X-Loqate-Api-Key header to the proxy, which forwards Find and Verify requests to Loqate. The key is persisted in localStorage and is not protected as a production secret.

Address formatting and standard

When available, Loqate's AddressFormat response determines the formatted address lines: each line identifies response fields, and non-empty values are joined for display. UPU S42 is the addressing reference used by the POC; the app does not implement a separate address standard engine.

Limitations: the proxy has no authentication, cache, account system, or secure server-side key store. Map display requires Leaflet CDN and OpenStreetMap access. This demonstration does not establish address deliverability, ownership, or legal status.

RECREATION SPECIFICATION

Application Recreation Specification

This document is the implementation specification for recreating the Address

Explorer POC if the source application is unavailable. It complements

[design.md](./design.md), which explains the architecture and research context.

Product purpose

Build a static browser application that:

  1. Searches international addresses through Loqate.
  2. Verifies a selected address and requests geocoding.
  3. Displays formatted and raw verified address fields.
  4. Shows search-result and verified-address locations on an interactive map.
  5. Provides a catalogue of recently verified addresses with local search and

country filtering.

This is a proof of concept. It is not an address database, an identity system,

or a deliverability/legal verification service.

Runtime shape

The application has no frontend build step or framework:

src/
  poc-address-app.html   Complete browser application and inline UI logic
  loqate-client.js       Browser API client and catalogue filtering helper
  config.js              ADDRESS_API_BASE_URL configuration
api/
  main.py                FastAPI Loqate proxy
  requirements.txt       FastAPI, httpx, and uvicorn
  Containerfile          Python container image
  start.py               Local/container server entry point
scripts/
  run-local.ps1          Starts the API and static client locally
  serve-client.js        Static file server
docs/
  index.html              Published copy of the application
  loqate-client.js        Published copy of the browser client
  config.js               Published API configuration

Leaflet 1.9.4 is loaded from unpkg.com. OpenStreetMap tiles are used for the

map. Both services require browser network access.

UI specification

The page contains:

  • A dark/light theme toggle. Persist the theme as

poc-address.theme.v1 in localStorage.

  • Country selector with GB, US, DE, FR, ES, IT, NL, BE, IE, PT, AU, and CA.
  • Address/postcode query input.
  • Loqate API key password input and save button. Persist it as

loqate_api_key.

  • Search button and status/error messages.
  • Search-results catalogue showing result text and description.
  • A compact map preview and an expandable full-size map dialog.
  • A verified-address detail panel.
  • A verified address catalogue with:

- refresh button;

- free-text local filtering;

- country filtering;

- record count;

- selectable records.

Selecting a search result or catalogue record must:

  1. Show the detail panel.
  2. Render the verified address.
  3. Center the map on valid latitude/longitude values.
  4. Create or update the marker.
  5. Open the marker popup.

Catalogue selection uses its cached details object and must not issue another

verification request.

Address rendering

If AddressFormat is present, split it on
tags. For each line, resolve

the field names against the verification response and display non-empty values.

If it is absent, display the Address field.

The raw field table excludes formatted/redundant fields including Address,

Address1-Address5, AddressFormat, delivery-format fields, quality/status

fields, Sequence, MatchRuleLabel, HyphenClass, ID, and Country.

Latitude and longitude are accepted only when numeric and within normal

geographic bounds.

Demo mode

Without an API key, use built-in fixtures:

  • tf26rf → 93 Teagues Crescent, Trench Telford TF2 6RF
  • EC2M 7NH → 1 Liverpool Street, London EC2M 7NH

Demo verification data must include address lines, AddressFormat, country,

postcode, latitude, longitude, AVC, and AQI. Demo mode does not populate

the server-side catalogue.

Client behavior

LoqateClient must expose:

search(apiKey, country, query)       // Promise<SearchItem[]>
retrieve(apiKey, result, country)     // Promise<VerifiedAddress>
catalog(apiKey, country = "")        // Promise<CatalogItem[]>
filterCatalog(items, query, country) // CatalogItem[]

filterCatalog performs case-insensitive local matching against the serialized

catalogue record and applies an optional exact country filter.

API and server behavior

The API contract is documented separately in [api-contract.md](./api-contract.md).

The proxy must:

  • forward the caller's Loqate API key only to Loqate;
  • never include the key in an error response;
  • recursively follow Loqate Find containers up to five levels;
  • cache successful search and verification results;
  • add successful verified addresses to the in-memory catalogue;
  • isolate cache and catalogue entries by an SHA-256 API-key fingerprint;
  • deep-copy cached values before returning them;
  • expire entries after five minutes by default;
  • cap each cache at 256 entries;
  • allow ADDRESS_CACHE_TTL_SECONDS=0 to disable caching.

The cache and catalogue are intentionally process-local and non-durable.

Configuration and operations

Required environment variables:

CORS_ORIGINS=*
ADDRESS_CACHE_TTL_SECONDS=300

Optional:

LOQATE_CA_BUNDLE=C:\path\company-root.cer

The API listens on port 8001. The local static client is served on port 5174.

Run the local environment with:

powershell -ExecutionPolicy Bypass -File .\scripts\run-local.ps1

Acceptance checklist

  • Search sends q, country, and X-Loqate-Api-Key.
  • Repeated identical searches do not call Loqate while the cache is valid.
  • Verification returns the first verified match and caches it.
  • GET /api/addresses/catalog returns verified records for the caller's key.
  • Catalogue query and country filters work without another API request.
  • Catalogue selection displays details and updates the map.
  • Invalid upstream JSON, timeouts, network errors, and upstream errors produce

explicit user-visible failures.

  • API keys never appear in logs, response bodies, or error details.
  • API tests cover forwarding, caching, catalogue retrieval, filtering, and

upstream failure handling.

API CONTRACT

Address API Contract

The API is a FastAPI proxy for Loqate. The default local base URL is

http://127.0.0.1:8001.

All address endpoints require:

X-Loqate-Api-Key: <caller Loqate key>
Accept: application/json

The proxy does not persist or expose the API key.

GET /health

Response:

{"status": "ok"}

GET /heartbeat

Response:

{"status": "awake"}

GET /api/addresses/search

Query parameters:

ParameterRequiredRules
------:---
qyes1-160 characters; address or postcode
countryyesTwo alphabetic characters; normalized uppercase

Example:

GET /api/addresses/search?q=tf26rf&country=GB
X-Loqate-Api-Key: caller-key

Response:

{
  "items": [
    {
      "id": "GB|RM|B|24490784|ENG",
      "text": "93 Teagues Crescent",
      "description": "Trench Telford TF2 6RF"
    }
  ]
}

The proxy calls Loqate Find with Limit=100. If the first response is a

container rather than an address, it follows the first container's Id using

Container, up to five levels.

POST /api/addresses/retrieve

Request:

{
  "id": "GB|RM|B|24490784|ENG",
  "text": "93 Teagues Crescent",
  "description": "Trench Telford TF2 6RF",
  "country": "GB"
}

Rules:

  • id and text are required non-empty strings.
  • description defaults to an empty string.
  • country is exactly two characters and is normalized uppercase.
  • Unknown request fields are rejected.

The proxy calls Loqate International Batch Verify with geocoding enabled and

returns the first item in Matches, or the item itself when Matches is

absent.

Example response:

{
  "Address": "93 Teagues Crescent<br>Trench<br>Telford<br>TF2 6RF",
  "Address1": "93 Teagues Crescent",
  "Address2": "Trench",
  "Locality": "Telford",
  "DependentLocality": "Trench",
  "PostalCode": "TF2 6RF",
  "CountryName": "United Kingdom",
  "ISO3166_2": "GB",
  "Latitude": "52.707846",
  "Longitude": "-2.460302",
  "AVC": "V44-I44-P6-100",
  "AQI": "A"

Successful verification adds a record to the process-local catalogue.

Optional query parameter:

ParameterRules

X-Loqate-Api-Key: caller-key

Response:

    {

      "description": "Trench Telford TF2 6RF",

The catalogue contains only successfully verified addresses. It is scoped by

the caller's API-key fingerprint and is not durable. An empty catalogue returns

{"items":[]}.

Errors

The proxy uses FastAPI validation responses (422) for invalid requests and:

StatusMeaning
---:---
502Loqate network failure, rejected response, invalid JSON, or unexpected payload
504Loqate request timed out

Error bodies use:

{"detail": "A human-readable message"}

Messages must not echo the API key.

Cache behavior

Successful search and retrieve requests are cached in process memory for five

minutes by default. Configure the duration with

ADDRESS_CACHE_TTL_SECONDS. Setting it to 0 disables storage and causes

catalogue records to expire immediately. Each cache is capped at 256 entries.

Cache keys include an SHA-256 API-key fingerprint, so callers cannot see another

caller's cached results.
